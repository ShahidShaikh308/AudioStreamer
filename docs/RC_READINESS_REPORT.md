# AudioStreamer Commercial Release Candidate Readiness

**Audit date:** 2026-10-13  
**Verdict:** **Not ready for RC or commercial distribution.**  
**Scope:** Windows v2 product and the Android/ESP32 components represented in this repository. This is an implementation audit, not an assertion that undocumented external CI runs or physical tests have passed.

## Executive summary

The repository contains substantial Windows v2 implementation: a .NET Engine and Service, Audio v3 and Control v1 transports, bounded Named Pipe IPC, WinUI client, a WiX MSI definition, test projects, and a Windows CI workflow. These are real implementation artifacts, not just architecture documents.

It is not a commercial release candidate. The repository has no selected license; no signed/released package or SBOM; the Windows service-account audio behavior and real LAN audio path are unqualified; update tooling creates/verifies metadata but does not update installed clients; version values reported to clients do not match the packaged product version; several declared UI operations are explicitly unavailable; and the current environment could not run the .NET build or tests. The checked-in test plan also explicitly leaves upgrade/rollback, supported-image, security, cross-device, and soak gates open.

## Findings by severity

### Critical — release blockers

1. **No distribution license or third-party notices.** No `LICENSE`, `NOTICE`, or third-party notices file exists. The README states that a license has not been selected and that the project is not ready for public redistribution ([README.md](/C:/Development/Python/AudioStreamer/README.md:114)). This prevents a commercial/public release until ownership and dependency licensing are resolved.

2. **The primary audio function is not qualified under the installed Service identity.** The MSI installs the Service as `NT AUTHORITY\\LocalService` ([Package.wxs](/C:/Development/Python/AudioStreamer/installer/Package.wxs:42)); audio capture/playback is created inside that Service process ([WindowsAudioSessionRuntime.cs](/C:/Development/Python/AudioStreamer/src/AudioStreamer.Platform.Windows.Audio/WindowsAudioSessionRuntime.cs:49), [WasapiCaptureBackend.cs](/C:/Development/Python/AudioStreamer/src/AudioStreamer.Platform.Windows.Audio/Internal/WasapiCaptureBackend.cs:23)). The documents explicitly require proof of capture/playback from the intended account and Session 0, including before login, after logoff, RDP, device changes, and sleep/resume ([WINDOWS_SERVICE.md](/C:/Development/Python/AudioStreamer/docs/WINDOWS_SERVICE.md:61)). No evidence of that hardware/session test is present; the installer validation script checks service startup and IPC, not audible capture/playback. This blocks claiming the core product function works when installed.

3. **No signed product release or distribution artifact is produced.** The workflow uploads an MSI as a CI artifact and does not sign it, generate an SBOM, publish a release, or create update metadata ([windows-rc.yml](/C:/Development/Python/AudioStreamer/.github/workflows/windows-rc.yml:43), [BUILDING.md](/C:/Development/Python/AudioStreamer/docs/BUILDING.md:7)). The installer specification requires signed packages/binaries, reproducible release metadata, and an SBOM ([INSTALLER_AND_UPDATES.md](/C:/Development/Python/AudioStreamer/docs/INSTALLER_AND_UPDATES.md:74)); the status section confirms these are still release-owner gates ([INSTALLER_AND_UPDATES.md](/C:/Development/Python/AudioStreamer/docs/INSTALLER_AND_UPDATES.md:88)).

### Major — must close before commercial release

1. **No installed-product update/rollback system.** `New-UpdateManifest.ps1` and `Test-UpdateManifest.ps1` sign and verify metadata, but there is no downloader, update scheduler, staging/transaction, rollback engine, or user-facing update flow ([INSTALLER_AND_UPDATES.md](/C:/Development/Python/AudioStreamer/docs/INSTALLER_AND_UPDATES.md:86)). The UI returns `CapabilityUnavailable` for `BeginUpdateCheck` and `GetVersions` ([EngineIpcRequestHandler.cs](/C:/Development/Python/AudioStreamer/src/AudioStreamer.Service/EngineIpcRequestHandler.cs:164)). A manual MSI servicing policy could be acceptable, but none is defined as the supported end-user update path. Automatic updates must not be advertised.

2. **Installer is a package scaffold, not the specified deployable setup.** There is an x64 MSI, service registration, SCM recovery configuration, data/log directories, and a Start Menu shortcut ([Package.wxs](/C:/Development/Python/AudioStreamer/installer/Package.wxs:1)). There is no bootstrapper, prerequisite/OS support check, prerequisite chaining, or installer UI path for clear failure/repair. The specification calls for those setup checks and a signed MSI/bootstrapper ([INSTALLER_AND_UPDATES.md](/C:/Development/Python/AudioStreamer/docs/INSTALLER_AND_UPDATES.md:9), [INSTALLER_AND_UPDATES.md](/C:/Development/Python/AudioStreamer/docs/INSTALLER_AND_UPDATES.md:19)). The RC script only performs install, service/IPC/log checks, optional process-crash recovery, and uninstall; upgrade, repair, rollback, config preservation, clean-image prerequisite, and ACL verification remain untested ([Invoke-RcValidation.ps1](/C:/Development/Python/AudioStreamer/tools/release/Invoke-RcValidation.ps1:1), [TEST_PLAN.md](/C:/Development/Python/AudioStreamer/docs/TEST_PLAN.md:133)).

3. **Reported version metadata is inconsistent with the installer version.** CI assigns the MSI `2.0.<run_number>` ([windows-rc.yml](/C:/Development/Python/AudioStreamer/.github/workflows/windows-rc.yml:43)), but projects do not define a shared product version, Engine reports its assembly version as `ProductVersion` ([Engine.cs](/C:/Development/Python/AudioStreamer/src/AudioStreamer.Engine/Engine.cs:329)), and the Service handshake hardcodes IPC version text `2.0.0` ([EngineIpcRequestHandler.cs](/C:/Development/Python/AudioStreamer/src/AudioStreamer.Service/EngineIpcRequestHandler.cs:29)) while the actual IPC schema constants are major 1/minor 0 ([IpcProtocol.cs](/C:/Development/Python/AudioStreamer/src/AudioStreamer.IPC.Contracts/IpcProtocol.cs:10)). Thus the installer, handshake, Engine version, and IPC schema do not provide the single coherent compatibility/version record specified for releases.

4. **Windows audio device operations are not exposed to the UI.** Although a Windows endpoint manager is registered, `GetAudioDevices` and `SelectAudioDevices` requests are hard-coded to return capability-unavailable ([EngineIpcRequestHandler.cs](/C:/Development/Python/AudioStreamer/src/AudioStreamer.Service/EngineIpcRequestHandler.cs:164)). The UI specification likewise marks endpoint selection and live device changes unavailable ([UI_SPECIFICATION.md](/C:/Development/Python/AudioStreamer/docs/UI_SPECIFICATION.md:125)). A commercial user cannot choose or manage the route’s audio devices through the product UI.

5. **Diagnostics UI is only a summary, not the specified operational log viewer.** The UI has support-summary copy/export, while its own spec says logs are not available to this client; log paging/search/filter/export and recent redacted logs are absent ([UI_SPECIFICATION.md](/C:/Development/Python/AudioStreamer/docs/UI_SPECIFICATION.md:15), [UI_SPECIFICATION.md](/C:/Development/Python/AudioStreamer/docs/UI_SPECIFICATION.md:61)). `GetLogsPage` is unavailable at the Service boundary ([EngineIpcRequestHandler.cs](/C:/Development/Python/AudioStreamer/src/AudioStreamer.Service/EngineIpcRequestHandler.cs:164)). This limits customer troubleshooting and supportability.

6. **Commercial UI requirements are knowingly incomplete.** The UI spec records no modern toast notifications, no tray direct stream actions, no update installation, and incomplete high-contrast/localization/reduced-motion verification ([UI_SPECIFICATION.md](/C:/Development/Python/AudioStreamer/docs/UI_SPECIFICATION.md:125)). The current unpackaged UI does not meet the documented toast activation prerequisites ([UI_SPECIFICATION.md](/C:/Development/Python/AudioStreamer/docs/UI_SPECIFICATION.md:126)). Decide which are release requirements and either implement/test them or revise the supported product specification before declaring RC.

7. **IPC authorization does not implement the documented role boundary.** The pipe DACL grants read/write to all `AuthenticatedUser` principals, and authentication only establishes that a client is authenticated ([WindowsPipeFactory.cs](/C:/Development/Python/AudioStreamer/src/AudioStreamer.IPC/Transport/WindowsPipeFactory.cs:60), [WindowsPipeFactory.cs](/C:/Development/Python/AudioStreamer/src/AudioStreamer.IPC/Transport/WindowsPipeFactory.cs:85)). The handshake validates a client-supplied `RequestedRole == "interactive"` ([VersionHandshake.cs](/C:/Development/Python/AudioStreamer/src/AudioStreamer.IPC/Protocol/VersionHandshake.cs:22)); the request dispatcher does not authorize stream/pause/resume mutations against a token-derived role, and only machine settings have an explicit administrator check. This is broader than the architecture’s client-token authorization/role-enforcement requirement ([ARCHITECTURE_RULES.md](/C:/Development/Python/AudioStreamer/docs/ARCHITECTURE_RULES.md:32)). Complete a threat/authorization review and enforce the intended local-user/session policy before release.

8. **Release verification is incomplete and not reproducible from this workspace.** There is no .NET SDK, so the solution build/tests were not run. The Python/.NET compatibility command ran 3 cases: the Python canonical fixture passed, while the two cross-runtime cases errored because `dotnet` was not found. The test plan says physical cross-device LAN, audio/session, soak, security, supported-image, update/rollback, and UI acceptance remain open ([TEST_PLAN.md](/C:/Development/Python/AudioStreamer/docs/TEST_PLAN.md:133), [TEST_PLAN.md](/C:/Development/Python/AudioStreamer/docs/TEST_PLAN.md:140)). No CI run evidence was available in this repository snapshot. RC cannot be declared until a clean Windows build and all release gates are attached to the exact candidate.

9. **Cross-platform release readiness is absent.** The workflow only builds/tests the .NET Windows solution and a Python/.NET audio fixture. It does not build Android or ESP32. Android `release` has code optimization disabled and no release signing configuration ([build.gradle.kts](/C:/Development/Python/AudioStreamer/platforms/android/app/build.gradle.kts:28)); no Android release pipeline/artifact or ESP32 firmware release process is present. If Android and ESP32 remain supported components of the commercial product, their build, signing/provisioning, compatibility, and release gates must be added.

10. **Automated test coverage does not match the production test plan.** Tests cover Engine lifecycle/managers, codec fixtures, buffer/audio adapter fakes, IPC framing/server, limited service logging/config migration, and UI-core navigation. There are no dedicated `ControlRuntime` tests, actual NodeHost/Service lifecycle or crash-boundary tests, installer transaction tests, IPC ACL/authorization tests, full UI automation, or Windows service-account audio integration tests. The broad integration/hardware tests remain specified but are not implemented or recorded as passing ([TEST_PLAN.md](/C:/Development/Python/AudioStreamer/docs/TEST_PLAN.md:27), [TEST_PLAN.md](/C:/Development/Python/AudioStreamer/docs/TEST_PLAN.md:68)).

### Minor — release hardening / maintenance gaps

1. **SCM retry delays do not increase.** MSI configures the first and second restart actions but assigns both the same 10-second delay; the service specification calls for increasing delays and sustained-health reset behavior ([Package.wxs](/C:/Development/Python/AudioStreamer/installer/Package.wxs:44), [WINDOWS_SERVICE.md](/C:/Development/Python/AudioStreamer/docs/WINDOWS_SERVICE.md:55)). Current actions are bounded (two restarts, then none), but policy and documentation should match.

2. **No automated dependency inventory/security gate.** No SBOM, dependency vulnerability scan, license inventory, or dependency pin verification job is in the workflow. Central package versions exist for .NET, but GitHub Actions are referenced by mutable major tags rather than immutable commit SHAs ([windows-rc.yml](/C:/Development/Python/AudioStreamer/.github/workflows/windows-rc.yml:16)). This is release supply-chain hardening; signed artifacts and dependency/license review are already Critical gates.

3. **Current repo entry points still identify the product as active development and prioritize the Python v1 launcher.** README says the v2 service/MSI are still in production-readiness validation and no supported release has been declared ([README.md](/C:/Development/Python/AudioStreamer/README.md:87)); the quick start still sends Windows users to a Python launcher. Update product onboarding and upgrade/support docs when the supported commercial edition and installation path are decided.

### Cosmetic — no cosmetic-only issue promoted to a release blocker

No purely visual defect was classified as a release blocker from this source-only review. WinUI layout, scaling, accessibility, and quality require the documented Windows UI acceptance pass; source inspection cannot certify the rendered experience.

## Verification performed

- Inspected the solution/projects, service startup and composition, Windows audio adapters/session runtime, IPC pipe ACL/handshake/dispatch, ControlRuntime, Engine version/API, WinUI shell/view models/pages, WiX MSI and project, release scripts, GitHub workflow, tests, Android Gradle configuration, README and release specifications.

- Ran `python -m unittest audio_plane.tests.test_protocol_dotnet_compat -v`: 1 passed; 2 errored because the `dotnet` executable is unavailable. No .NET build/test, MSI build/install, Android release build, ESP32 build, or hardware test is claimed as passing.
- Made no product-code changes as part of this audit.

## RC exit criteria

Do not label or publish this as RC until all Critical items are resolved and all Major items either meet the approved commercial scope or are removed from release claims with explicit owner acceptance. At minimum, attach evidence for: licensing and notices; signed installer/binaries and SBOM; consistent version metadata; successful clean Windows build/test and MSI validation; service-account audio capture/playback; Windows ↔ Android/ESP32 LAN operation in both directions; upgrade/repair/rollback/uninstall; IPC authorization; UI/accessibility acceptance; and the required soak on the exact signed candidate.
